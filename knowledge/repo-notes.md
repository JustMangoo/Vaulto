# Repo Notes

_Last updated: 2026-08-28_

Repo: github.com/JustMangoo/Vaulto. Structure was originally `client/`
(Vue 3 + Vite + TS SPA) and `server/` (Express + Mongoose/MongoDB +
Multer) - being rebuilt per `stack.md`.

## Git gotchas found (worth fixing/watching during the restart)

- `node_modules` (both client and server) was tracked in git history -
  6,030+ files at one point. This is almost certainly why `git status` can
  hang/time out on this repo when run over a network-mounted filesystem (it
  has to diff thousands of dependency files). Fix: `node_modules` is in the
  root `.gitignore`, and already-tracked copies were untracked with
  `git rm -r --cached node_modules server/node_modules` (adding a
  `.gitignore` rule alone does not untrack already-committed files).
- Only `client/.gitignore` existed originally (auto-generated by the
  Vite/Vue scaffolding tool) - nothing at the repo root or inside `server/`.
  A root `.gitignore` was added Aug 23 2026, starting with just `.idea/`,
  expanded since to cover `node_modules`/`dist`/`.env`.
- Real uploaded images were committed under `server/uploads/*.png/jpg`
  (timestamped filenames like `1754969010504-119762267.png`) on the old
  build - worth keeping in mind if that history ever needs cleaning up.
- `git status` / `git status --untracked-files=no` can hang on this repo
  over a network-mounted filesystem; `git log`, `git branch -a`,
  `git ls-files`, `git rev-list --count` all work fine and are fast -
  prefer those when checking repo state remotely rather than `git status`.
- Branch `restart` was created off `main` (identical commit at branch time,
  no divergence) as the place to rebuild from scratch while `main` stays as
  the untouched archive of the old Collections/Items-based build.

## Update (2026-08-28): server/ -> repo root move

`server/` has been flattened into the repo root (see `stack.md`). Practical
notes from doing it:

- A first attempt via a PowerShell loop on Windows got about halfway
  through, then every remaining `git mv` failed with a stale
  `.git/index.lock` ("Another git process seems to be running") - almost
  certainly PhpStorm's background VCS integration grabbing the lock at the
  same moment (`.idea/` was being touched at the exact same timestamp).
  That attempt was fully rolled back (`git mv` back to `server/...` for
  everything that had moved, `git checkout -- package-lock.json` to drop an
  accidental `npm install` that had run against the half-moved
  `package.json`) before redoing it properly in one continuous script.
- `package-lock.json` existed at both the repo root (a leftover ~85-byte
  empty stub) and inside `server/` (the real one). Resolved by `git rm`-ing
  the root stub first, then moving the real one into its place.
- Root only ever had `.gitignore`/`README.md`/`package-lock.json` before
  the move; `server/` had its own `.gitignore` (the actual Laravel-default
  one) and no `README.md`. The two `.gitignore`s were merged rather than
  one overwriting the other.
- `vendor/` and `node_modules/` were deliberately left behind in the old
  `server/` folder rather than moved - both are git-ignored, and bulk file
  operations (move, delete) on folders that size are very slow over a
  network-mounted connected folder, the same class of issue as the
  `git status` slowness noted above. Run `composer install` and
  `npm install` at the new repo root to regenerate them there; the old
  `server/` folder (now just containing the stale `vendor/`/`node_modules/`)
  is safe to delete locally whenever convenient - deleting it directly on
  Windows is fast, no need to route that through anything remote.
